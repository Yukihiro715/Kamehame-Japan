# コンテンツの入稿方法

記事・口コミ・体験情報の3つについて、誰がどう更新するかをまとめます。

## 結論:当面はチャットで依頼、CMSは入れない

記事も口コミも体験情報も、リポジトリ内のデータファイルに置いています。
更新は「伊藤さんがClaudeに依頼 → 反映 → mainへプッシュ → 自動公開」です。
ブラウザで編集する管理画面はありません。

CMS(microCMSなど)を入れなかった理由:

- 月額費用と運用の学習コストがかかる
- 3言語ぶんの入稿画面を作り込む必要があり、記事が月1〜2本ならその手間が回収できない
- いまの体制では記事を書くのがClaudeなので、管理画面を経由する意味が薄い

**社内に編集担当者を置く段階になったら**、microCMSへの移行を検討してください。
記事データは `lib/articles.ts` の構造がそのままAPIのスキーマになるため、
移行は1日程度で済みます。

## 記事(読みもの)

ファイル: `lib/articles.ts`

依頼の仕方 — 次の材料があれば記事を書きます。無くても構いません。

- テーマ(例:「茶室に入るときの作法」)
- 関連づけたい体験(その体験ページに関連記事として表示されます)
- 事実として確かな情報(受け入れ先から聞いた話、現地で確認したことなど)

記事は**言語ごとに独立**しています。英語だけ、日本語だけ、という状態で問題ありません。
書かれていない言語では、その記事は一覧にも出ず、URLも生成されません。

掲載先は自動で3か所:

1. `/{lang}/journal/` の一覧
2. トップページの「読みもの」セクション(最新3本)
3. `experiences` に指定した体験の詳細ページ(「あわせて読む」)

記事が0本のときは、一覧ページが「執筆中」の案内に切り替わり、
トップページと体験ページのセクションは**そもそも表示されません**。
中途半端な枠が残ることはありません。

記事は `experiences` に指定した体験のうち**1つ以上がサイトに掲載されている間だけ**公開されます。
提携前の体験だけに紐づく記事(相撲の稽古見学のマナー、江戸前寿司、料金の内訳)は、その体験が
`live` になるまで一覧・サイトマップから自動的に外れます。料金の内訳の記事は寿司の数字で書かれているため、
お座敷の数字で書き直してから `evening-with-geiko` を紐づけ直してください。

## 口コミ

ファイル: `lib/reviews.ts`

**現在 `REVIEWS_PUBLISHED = false` です。** 実際のお客様の声が集まるまで、
サイトには「販売開始後に掲載します」という表示が出ます。

いま入っているデータはレイアウト確認用のサンプルで、実在のお客様の声ではありません。
作り話のレビューを公開することは、訪問者に対して率直でないというだけでなく、
存在しない評価を構造化データで宣言することになり、Googleのポリシー違反として
ドメイン全体にペナルティが課されるおそれがあります。
そのためフラグを false にしてあります。

公開手順(実際のレビューが集まったら):

1. `SAMPLE_REVIEWS` を実際のレビューに置き換える
2. `REVIEWS_PUBLISHED` を `true` にする
3. 星・件数・レビュー一覧・構造化データが同時に有効になります

### 口コミ取得フロー(設計)

**取得の設計方針:** 集めやすさより、後で使える形で集めることを優先します。
Googleの口コミは検索とマップに効き、自社サイトの口コミはコンバージョンに効きます。
両方必要なので、**1通のメールで両方に導線を出します**。

体験終了の翌日、参加者へメールを送ります(Bókun接続後は自動送信)。

1. **体験翌日 10:00(現地時間)** — お礼メール
   - 写真があれば添付(これが開封率を大きく上げます)
   - 「よろしければ一言お聞かせください」+ **★1〜5のボタン**
2. **★4〜5を押した方** → Googleレビューの投稿画面へ直接遷移
   - Googleビジネスプロフィールのレビューリンクを使用
   - ここが検索評価に効きます
3. **★1〜3を押した方** → Googleではなく**当方への意見フォーム**へ
   - 低評価を隠すためではなく、**先に事情を聞いて解決するため**です
   - 解決したうえで、改めて投稿をお願いするかはご本人の判断に委ねます
4. **7日後** — 未回答の方へリマインド1回のみ(それ以上は送らない)

サイトに載せるレビューの扱い:

- **選んで載せない。** いただいたものは低評価も含めて掲載します
  (高評価だけを並べたページは、読み手にすぐ見抜かれます)
- 氏名はイニシャルのみ、国名を併記
- Bókun経由の予約に紐づくものだけ「予約確認済み」を表示

受け入れ先には、**レビュー依頼の送付への同意**を条件確認シートで取っています。

## 体験情報

ファイル: `lib/catalog.ts`(英語)、`lib/catalog.ja.ts`、`.es.ts`、`.fr.ts`、`.zh-tw.ts`

**掲載されるのは `status: "live"` の体験だけです**(`lib/catalog.ts` の `PLACEHOLDERS_PUBLISHED = false`)。
提携前の体験(寿司・相撲・茶道など)はデータとして残っていますが、サイト・ナビ・サイトマップには一切出ず、
URLも404になります。体験が1つだけのあいだ、トップページはその体験を1枚の大きなカードで見せ、
都市・ジャンルの一覧は自動で消えます(2つ以上になれば元の一覧に戻ります)。

提携先が決まったら、その体験の `status` を `"live"` にするだけで、一覧・ナビ・サイトマップ・トップページに
自動で載ります。提携前の体験を「近日公開」ラベル付きで見せたくなった場合は `PLACEHOLDERS_PUBLISHED` を
`true` にしてください。

提携先から条件確認シートが返ってきたら、その内容をそのまま渡してください。
5言語ぶんを作成し、共有カード(1200×630)も生成します。

体験詳細ページは次の順で組まれます。データが無い項目は自動で非表示(トルツメ)になります。

| 表示ブロック | データ項目 | 無いとき |
| --- | --- | --- |
| ファーストビュー(写真・見出し・条件ラベル・料金・ボタン) | `title` `tagline` `duration` `group` `price` `priceUnit` | 必須 |
| 口コミ要約 / 口コミ詳細 | `lib/reviews.ts`(`REVIEWS_PUBLISHED`) | 非表示 |
| 動画(クリックで再生) | `video: { kind, src, poster, aspect }` | 非表示・「動画を見る」リンクも消える |
| 写真ギャラリー(スワイプ/一覧) | `img` + `gallery[]`、注記は `galleryNote` | メイン写真のみ |
| 特徴3枚 | `highlights[]`(3件) | サイト共通の3枚を表示 |
| 料金表(人数別・合計と1名あたり)、繁忙期 | `pricing.tiers` `pricing.highSeason` | `price` から算出 |
| 含まれるもの / 含まれないもの | `included[]` `notIncluded[]` | 「通訳同行」のみ表示 |
| 当日の流れ(縦タイムライン) | `schedule[]`(`time` `title` `body` `img`) | `itinerary` から生成 |
| 会場(今わかること / 予約確定後) | `venue.known[]` `venue.afterBooking[]` `venue.img` | エリア名のみ |
| FAQ | `faq[]` + サイト共通3問 | 共通3問のみ |
| 予約の流れ・キャンセル規定・問い合わせフォーム | `cancellation` | サイト共通の規定 |

人数・料金・動画・公開状態(`status`)などの構造データは英語ファイルだけに書けば全言語に反映されます。
各言語ファイルには文言だけを書きます。

写真は**横長・長辺1600px以上**をお願いしてください。
縦長しか無い場合はこちらでカード化しますが、見栄えは横長のほうが確実に良くなります。
