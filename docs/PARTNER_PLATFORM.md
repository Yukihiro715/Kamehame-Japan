# 提携パートナープラットフォーム（Step 2: 一般化と精算 ／ Step 3: 予約取り次ぎ）

設計は `docs/PARTNER_PLATFORM_STAGE1.md`。ここでは Step 2 で入ったものと運用手順をまとめる。ホテル紹介の段階 2・3（`docs/HOTEL_REFERRAL.md`）はそのまま土台。

## 2a. 提携パートナーへの一般化（移行 0008）

- 契約先（`partner_legal_entities`）に **種別**（ホテル / 旅行代理店 / ガイド / その他）、**形態**（法人 / 個人）、連絡先メール。
- 拠点（`hotels` テーブル、画面では「拠点」）に **拠点種別**（施設 / 支店・拠点 / ガイド本人 / その他）と **使える機能** `features_json`: `refer`（リンク紹介）、`cases`（予約取り次ぎ、Step 3）、`settlement`（精算閲覧・確認）、`members`（メンバー管理、Step 3）。種別と機能は独立。
- 役割に `partner_agent`（取り次ぎ担当）と `partner_manager`（拠点管理者）を追加。`cases` が有効な拠点でだけ招待できる。既存の閲覧担当者・請求担当者はそのまま。
- 機能の判定はサーバー（`lib/portal/partner.ts` の `requireFeature`）。`refer` を切った拠点は、リンク・QR の新規発行ができず、`/r/<token>` は通常ページへ案内するだけで紹介セッションを作らない（既存セッションの予約は影響なし）。
- 運営 → 提携パートナー: 契約先の登録で「拠点も同時に作る」を選ぶと、個人ガイドや支店のない代理店を 1 回で登録できる（契約先と同名の拠点と精算設定ができる）。拠点の詳細で種別と機能を切り替える。
- 既存データの移行はなし（列追加と既定値のみ）。公開 ID、照合番号、リンクのトークンは変わらない。

## 2b. 精算（段階 4、移行 0009）

### 流れ

1. **締め**（運営 → 精算、経理または管理者）: 四半期が終わったら対象四半期（例 `2026-Q3`）を入力して実行。精算先ごとに下書きの「お支払い通知書」ができる。対象は、実施確認済みで保留のない確定紹介料のうち通知書に未収載のもの（遅れて確定した前四半期分も含む）と、発行済み通知書に載った予約の訂正明細（`commission_adjustments`）。何度実行しても下書きを作り直すだけで、発行済みには触れない。
2. **発行**: 通知書の詳細で「発行する」。請求担当者（いなければ契約先の連絡先メール）に通知メール。異議申立て期限 = 発行日 + 精算設定の `dispute_days`（既定 14 日）。
3. **確認 / 異議**（パートナー → 精算）: 請求担当者が「内容を確認しました」か「異議を申し立てる」（通知書全体または明細ごと、理由必須）。期限を過ぎて無反応なら 5 分おきの cron が自動で確認済みにする。期限後の異議は受け付けない。
4. **異議への回答**（運営）: 「原案どおり」なら発行済みに戻る。「認容」なら予約の明細・実施記録・料率を訂正してから通知書を **無効** にし、同じ四半期を締め直すと **訂正版（版 2）** ができる。無効にした版も履歴として読める。
5. **支払バッチ**（運営 → 支払）: 支払日を指定して作成。その日までに支払予定で振込額のある通知書（発行済み・確認済み）を精算先ごとに 1 振込にまとめる。「振込リスト CSV」を銀行のツールに取り込み、結果（支払済み / 失敗 / 保留）と参照番号を登録する。支払済みで通知書は「支払済み」、パートナーに完了メール。失敗は次のバッチに再び載る。銀行への自動送金はしない。

### 金額の決まり（`lib/portal/settlement.ts`）

- 紹介料は予約ごとに四捨五入済みの台帳値。消費税は通知書の税抜合計に対して 1 回（T09）。
- 繰越: 直前の通知書（発行済み以降）の「次回繰越」を「前期からの繰越」に入れる。お支払い対象額 = 税込合計 + 繰越。
- 最低お支払額（精算設定 `min_payout_jpy`、既定 3,000 円）は **税込の対象額で判定**。未満なら全額を次回へ繰越し、振込額 0。
- 振込手数料（`bank_fee_jpy`、`fee_borne_by = 'hotel'` のとき）は振込額からだけ差し引く（T11/T12）。
- 返金で対象額がマイナスになったら、そのまま次回へ繰越して相殺する（T28）。
- 支払日 = 四半期末の翌月末。土日なら前営業日（祝日は未考慮。必要なら運営がバッチの支払日で調整）。

### 帳票

- 通知書は画面（`/hotel/settlement/<id>/`、`/ops/settlement/<id>/`）の「印刷 / PDF保存」でブラウザから PDF にする（D-2 案 A）。明細 CSV も同じ数字。
- 記載: 宛先（契約先名・所在地・登録番号）、発行者、期間、通知書番号、税抜・消費税・税込・繰越・対象額・次回繰越・手数料・振込額・振込予定日、明細、注記（算出方法、繰越、異議期限、支払通知書方式）。税務上の記載事項の追加は経理確認のうえ `components/portal/statement-sheet.tsx` を直す。

### テスト

`tests/settlement.test.mjs`（締め・繰越・最低額・手数料・再実行・発行・確認・異議・訂正版・支払バッチ・CSV・自動確認）、`tests/partner-platform.test.mjs`（種別と機能の独立、個人ガイド、紹介スイッチ）。既存の `portal-api`、`referral-*` は変更なしで通る。

### 本番に必要な設定

- 追加のシークレットはない。移行 0008・0009 はデプロイで自動適用。
- 精算先ごとの条件（最低額、手数料負担と金額、異議日数）は当面 SQL で更新する（`settlement_profiles`）。画面からの編集は Step 3 以降。
- 口座情報は `bank_details_masked`（表示用）のみ運用。暗号化保存（`bank_details_enc`）は未実装のため、振込リスト CSV はマスク表示で、実際の口座は銀行側の登録を使う。

## 3. 予約取り次ぎ（移行 0010、`lib/portal/cases.ts`）

パートナーがお客様のご希望を案件として登録し、運営が見積もりを作ってお客様向けページで決済まで進める流れ。予約の紹介元は **案件の拠点に直接固定**（`reservation_referrals.basis = 'case'`）され、Cookie や端末に関係なく紹介料まで同じ帰属で進む（要件 5-2、T-N03）。

### 画面

| 誰 | URL | できること |
|---|---|---|
| パートナー（取り次ぎ担当 / 拠点管理者） | `/hotel/cases/`、`/hotel/cases/new/`、`/hotel/cases/<id>/` | 案件登録（体験 or 自由相談、希望日・代替日・人数・言語・条件、代表者名と連絡先、担当、管理番号、商品別の追加項目＝ゴルフ 9 項目）、進捗確認、お客様向け URL のコピー、紹介料の見込み、運営との連絡・添付、未決済案件の取り下げ |
| パートナー | `/hotel/experiences/` | 体験ごとに「予約する / 空きを確認する / 見積もりを依頼する」ボタン（`bookingType` と `pricePending` から判定）→ 案件登録へ |
| 運営（予約運営） | `/ops/cases/`、`/ops/cases/<id>/` | 案件の編集（自由相談への商品割当て、担当）、状態変更、見積もり作成（明細・含む/含まない・現地払い・キャンセル条件・確定条件・有効期限・支払い方法）、共有（お客様へのメール送付は任意）、取り下げ、予約確定、連絡（運営内部 / パートナー / お客様にも表示）と添付 |
| 運営（経理） | `/ops/cases/<id>/` | 提携先払い・現地払いの見積もりに対する「決済済み」登録（乗合バスゴルフなど） |
| お客様 | `/{lang}/quote/<token>/` | 見積もり内容・総額・含む/含まない・現地払い・キャンセル条件・有効期限・確定条件・「お客様にも表示」の添付・決済ボタン。パートナー名・紹介料・案件番号・内部メモは出ない（T-N07） |

取り次ぎ担当（`partner_agent`）は自分が登録または担当する案件、拠点管理者（`partner_manager`）は拠点の全案件を見る。閲覧担当者・請求担当者は案件を見られない。拠点の「予約取り次ぎ」機能が OFF なら API は `feature_off`（T-N08）。

### 流れと状態

1. 登録（`received`）→ 運営へメール。
2. 運営が確認（`checking` / `awaiting_customer` は手動）、見積もりの下書き → **共有**。共有で (a) 前の共有版は `superseded` にして Stripe の Checkout セッションを失効、(b) 予約台帳に仮予約を作成（2 回目以降は明細を差し替え）、紹介元を案件の拠点に固定、(c) 共有トークンを発行、(d) パートナーへメール（`notifyCustomer` でお客様にも）。状態は `awaiting_payment`（オンライン決済）または `proposed`（提携先払い・現地払いのみ）。
3. お客様がページの「カードで支払う」を押すと、その時点で Checkout セッションを作る（24 時間以内なら再利用、有効期限を超えない）。`client_reference_id = KJ-C-<見積もり id>`、`metadata.booking_flow = partner_case`、`metadata.reservation_id`。
4. Stripe の Webhook（`lib/payment-webhooks.ts`）→ 既存の台帳処理で決済を予約に記録 → 見積もり `paid`、案件 `paid` → パートナーと運営へメール。Sheets 自動化へは転送しない。同じイベントの再送は `duplicate` で何も増えない（T-N04）。
5. 運営が空き枠を確保して **「予約確定を登録」** → 予約 `confirmed`、案件 `confirmed`、パートナーへメール。決済済みと予約確定は別の事実（T-N05）。
6. 実施確認以降は既存の紹介料フローと同じ（`performed` は予約の `completed` から導出）。

パートナーに見せる状態は 4 軸（案件・見積もり・予約・紹介料）から `displayStatus()` で導出し、保存しない。

- 見積もりを変更するときは新しい版を作って共有する。旧版の URL は「新しい見積もりがあります」と案内して最新版へ誘導し、旧セッションは失効済み。失効前に決済が通った場合は予約に記録されるが、明細と総額が合わないため `amount_status = pending` で保留になり、例外一覧で運営が処理する（T-N06）。
- 有効期限（既定 7 日）を過ぎた共有版は cron（5 分ごと）で `expired` にしてセッションも失効。
- 決済済みの案件には新しい版を作れない。返金・差額は予約台帳で扱う。
- 乗合バスゴルフ（`golf-bus`）: 支払いは提携旅行会社へ。見積もりの支払い方法を「提携先への支払い」にして共有し、経理が「決済済みを登録」。紹介料の対象額はお客様表示のツアー代金（税込）から税抜計算（料率は `experience_referral_policies` の `golf-bus`）。

### 通知（E-8）

パートナー宛: 見積もり共有、決済完了、予約確定、運営からの連絡。運営宛: 新規案件、お客様決済、パートナーからの連絡。宛先は設定 `ops_notify_email`（未設定なら `CONTACT_TO`）。お客様宛（任意）: 見積もりリンク（英語 / 日本語）。検証環境では `NOTIFY_ALLOWLIST` の宛先にしか出ない。

### 添付

MEDIA バケットの `cases/<案件 id>/` に置く（PDF・画像・テキスト、15MB まで）。配信は `/api/portal/hotel/case-file?key=`（パートナー: `internal` 以外）、`/api/portal/ops/case-file?key=`、お客様は `/api/quote/<token>/file?key=`（`customer` の添付のみ）。

### テスト

`tests/cases.test.mjs`: T-N03/T-N04/T-N05（案件→共有→Webhook→帰属・重複なし・確定の分離）、T-N06（旧版の失効と誤決済の保留）、提携先払い（乗合バス）、T-N08（権限・内部メモ・自由相談・取り下げ）、有効期限。

### 本番に必要な設定

- 追加のシークレットはない。Checkout セッションの作成と失効は既存の `STRIPE_CHECKOUT_KEY`、Webhook は既存のエンドポイントとシークレットを使う（`checkout.session.completed` が届いていればよい）。
- 運営宛通知の `ops_notify_email` を `/ops/settings/` で設定する（未設定なら `CONTACT_TO`）。
- 乗合バスゴルフの紹介料率は `/ops/policies/` で `golf-bus` を登録する。

## 5. 言語（パートナー向け画面の多言語化、移行 0011）

パートナー向け画面（`/hotel/`）は日本語と英語で使える。運営画面（`/ops/`）は日本語のみ。

- 辞書は `components/portal/i18n.ts`（`ja` が原文、`en` は型で全キーを強制）。画面の文言・状態名・帳票（お支払い通知書）・エラー文・使い方ページはすべて辞書から出す。サーバーが返す日本語ラベル（`statusJa` など）は使わず、コードをクライアントで訳す。
- 言語の決まり方: サインイン前はブラウザの保存値（`localStorage`）、なければブラウザ言語。サインイン後は **ユーザーの保存言語**（`users.lang`）が優先し、ヘッダーの切替で変えると `POST /api/portal/hotel/lang` で保存される。
- メールも同じ言語: サインインコード、招待、見積もり共有、決済完了、予約確定、連絡、支払通知書発行、異議回答、振込完了（`lib/portal/mail.ts` の `lang`）。招待時は運営が `lang` を指定できる（既定 ja）。お客様向けの見積もりメールはお客様の言語（en/ja、それ以外は en）。
- 体験名はカタログの英語版（`titleEn`）を API が併せて返し、クライアントが言語で選ぶ。ゴルフの追加項目のラベルは辞書側で英訳。
- 日付は JST のまま、表記だけ言語に合わせる（`jst()`）。金額は ¥ 表記で共通。
- 使い方ページ `/hotel/guide/`: 画面の役割、取り次ぎの流れ、精算と紹介料の計算、サインイン方法を言語別に説明。
- 追加言語（繁体字中国語・スペイン語・フランス語）は `PortalLang` と辞書に 1 言語ずつ足せば画面は揃う。メール側は `MailLang` の追加が必要。

## 共通・パートナー別紹介料率（2026-11-13）

`/ops/policies/` の上部で管理者・経理が設定する。紹介対象の体験について、パートナー（契約法人・個人）の個別料率 → 共通料率 → 既存の体験別料率の順に適用する。個別料率は同じパートナーの全拠点に適用し、0%も有効。解除は履歴として保存し、下位の設定に戻す。体験の紹介停止・未設定、税率や紹介対象金額の条件は変えない。

設定は保存時以降または指定した将来日時から有効。予約作成時に料率と設定IDを固定するため、改定後も既存予約の料率は変わらない。紹介元を別パートナーへ訂正する場合のみ、その予約日時の訂正先条件を適用する。パートナー画面の体験一覧と見積もりにも同じ料率を表示する。設定変更は監査ログに記録する。

既存の `HP-DEMO` / `site-prosent-demo` の名称を「デモ用」に統一。所属パートナーは「株式会社プロセント（デモ）」、既存メンバーと権限を引き継ぐ。デモ拠点は通常の管理機能を使う確認用拠点であり、決済サンドボックスではない。サンプル予約・支払いは投入しない。

## パートナーメニュー・共有デモログイン（2026-11-13）

PC/スマートフォン共通で、左上のハンバーガーから左側の縦一列メニューを開く。背景クリック・閉じるボタン・Escapeで閉じ、キーボードフォーカスをメニュー内に保つ。

`/hotel/` の通常ログインフォームに `demo@kamehame-japan.com` と指定パスワードを入力する。デモ専用ボタンは表示しない。一般パートナーもメールアドレスとパスワードでログインする。指定パスワードはPBKDF2-SHA256、ランダムsalt、100,000回でハッシュ化してDBに格納し、平文をコード・クライアント配信物に含めない。

共有デモは新規の専用拠点 `HP-DEMO-PUBLIC` のみ、2時間セッション、閲覧専用。サーバーでホテルAPIの書込みをすべて拒否し、既存の社内デモや他パートナー・運営APIにアクセスさせない。IPごと15分10回のログイン試行上限、無効化・権限取消・ログアウトを適用する。通常のOTPや招待ではこのIDにアクセスを追加できない。

既存 `HP-DEMO` は「デモ用（社内確認）」として保持。共有デモには予約や精算のサンプルは入れず、個人情報を登録しない。パスワード変更は新しいsaltとハッシュで `demo_credentials` を更新し、当該ユーザーの既存sessionsを失効させる。
